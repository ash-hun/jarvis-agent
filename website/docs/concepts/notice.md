# Notice

jarvis-agent 의 기능을 한 표에 모으고, 그 기능을 어떤 원칙으로 만드는지 적는다. 이름을 누르면 그 기능의 설명 페이지로 간다. 각 페이지는 무엇을 하는지, 어떤 순서로 도는지(흐름도), 코드의 어디에 있는지(구현 위치)를 같은 순서로 다룬다.

:::note
흐름도와 설계도의 정본은 각 기능 페이지 하나뿐이다. 이 페이지의 기능 목록은 표만 두고 같은 그림을 다시 그리지 않는다.
:::

## 구현 철학

JARVIS 는 코드와 운영에서 몇 가지 원칙을 지키고, 그 원칙이 제품의 동작에 그대로 드러나게 만든다.

원칙의 원문은 레포의 `CLAUDE.md` 다. 이 절은 왜 그렇게 하는지와 제품에 어떻게 드러나는지를 적는다.

### 사고와 응답을 분리한다

이것이 제품의 중심 결정이다. 사용자 입력 하나마다 LLM 을 두 번 부른다.

- **메인 응답**: 도구를 쓰고 답을 만든다. 사용자가 보는 것은 이쪽이다
- **내적 사고**: 같은 입력을 보고 "무엇이 들어왔나, 의도는, 먼저 말할까, 뒤에서 할까, 약속이 생겼나" 를 JSON 으로 된 사고 프레임(`ThoughtFrame`)으로 낸다. 사용자에게는 💭 한 줄로만 보인다

둘을 섞지 않는 이유는 셋이다. 첫째, 사고 모델을 메인과 다르게(더 작고 싸게) 둘 수 있다. 둘째, 사고 결과를 구조화된 데이터로 저장하므로 정책이 그것으로 판단할 수 있다. 셋째, 사고가 느려도 응답을 막지 않도록 시점을 고를 수 있다(`before`, `race`, `after`).

사고 층은 벤더 스키마도 MCP 도 모르고 `model_layer` 에만 의존한다. 오케스트레이션과 정책은 `core` 가 맡는다.

### 먼저 말하기 전에 게이트를 지난다

먼저 건네는 말은 사고 프레임의 `utterance` 만 쓴다. 해석문은 사용자를 3인칭으로 분석한 문장이라 그대로 내보내지 않는다. 발화는 확신도 임계치, 쿨다운, 빈 발화 검사를 전부 지나야 하고, JARVIS 는 침묵한 이유를 로그에 남긴다. 저위험 자율 행동은 화이트리스트에 있고 승인도 필요 없는 도구만 실행한다.

사람이 승인해야 하는 것은 사람에게 묻는다. `bash`, `write_file`, `edit_file` 은 실행 전에 묻고, "항상 허용" 규칙은 사용자가 그 버튼을 눌렀을 때만 생긴다.

### 멱등성: 두 번 해도 한 번 한 것과 같게

멱등성을 지키는 이유는 복구다. 멱등하지 않으면 중간에 죽었을 때 사람이 현재 상태를 손으로 파악해야 한다. 멱등하면 다시 실행하는 것으로 끝난다.

- **무엇이 같은 것인지 먼저 정한다.** 절차 학습의 자연 키는 `<session_id>#<메시지 인덱스>` 이고, 같은 구간은 두 번 배우지 않는다. 승인 기억의 자연 키는 `(도구, 패턴)` 쌍이다
- **상태를 만들지 않고 맞춘다.** `CREATE TABLE IF NOT EXISTS`, `exist_ok=True`, upsert 를 쓴다. 세션 삭제는 없는 세션을 지워도 같은 결과를 낸다
- **확인과 변경 사이의 틈을 없앤다.** 코드의 중복 검사는 UX 용이고, 실제 보증은 DB 제약이 한다
- **결정과 부수효과를 섞지 않는다.** 정책은 순수 함수로 두고 I/O 는 경계에서 한다. 그래서 먼저 건네는 말의 게이팅은 LLM 없이 데이터셋으로 평가한다
- **비결정적 값은 경계에서 주입한다.** `uuid4()`, `datetime.now()` 를 로직 안에서 부르지 않는다. 테스트는 시계를 고정한다

### 최소주의와 수렴, 그리고 투영

세 원칙은 같은 것을 세 층에서 말한다.

- **최소**: 안 지은 코드가 가장 재현 가능하다. 구현체가 하나뿐인 인터페이스나 제품이 하나뿐인 팩토리는 만들지 않는다
- **수렴**: 지은 것은 두 번 실행해도 같은 상태로 간다. 의존성은 `uv.lock` 으로 고정하고, 실행은 `docker compose up -d` 로 하며, 이미지 태그에 `latest` 를 쓰지 않는다
- **투영**: 문서는 코드에서 유도한다. API 명세와 화면 명세는 `docs/` 의 두 파일로 고정하고, 엔드포인트나 화면을 고치는 작업 안에서 같이 고친다. 문서에 생성 시각이나 버전 번호를 박지 않는다

### 감수한 한계는 코드에 표시한다

의도적 단순화는 `# ponytail: <한계>, <업그레이드 조건>` 마커로, 의도적 비멱등은 `# idempotent: <이유>, <해결 방법>` 마커로 남긴다. 표시되지 않은 의도는 버그와 구분되지 않기 때문이다. 예를 들어 약속 중복 판정은 열린 약속을 매번 다시 임베딩한다. 그 자리에 "세션당 열린 약속이 수십 건을 넘으면 벡터를 레코드에 저장한다"는 업그레이드 조건이 적혀 있다.

### 코드 스타일

- 모듈은 기능 단위(`openloop/`, `procedures/`)로 나눈다. 종류별(`utils.py`, `services.py`)로 나누지 않는다
- `class` 는 유지할 상태나 주입할 의존성이 있을 때만 쓰고, 없으면 함수로 쓴다
- 주석에는 왜(why)만 적는다. 설명이 코드보다 길면 설명을 지운다
- 작업을 끝내기 전에 "이걸 지금 한 번 더 실행하면 어떻게 되나" 에 말로 답할 수 있어야 한다
