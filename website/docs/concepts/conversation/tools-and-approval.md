# Tool & Approve System

에이전트가 실제로 일을 하려면 파일, 셸, 웹을 다뤄야 하고, Jarvis-Agent는 이 모든 접근을 도구(Tool)로만 허용한다. 위험할 수 있는 도구는 실행 전에 사람에게 묻고, 사람이 한 번 허락한 범위는 기억해 다음부터 묻지 않는 Approve System을 함께 둔다. 도구 호출 한 번은 허용 목록, 플러그인, 승인 검사를 차례로 지나고, 여러 번 성공한 작업은 다시 쓸 수 있는 절차로 남고, 실패한 작업은 반성을 거쳐 그 절차를 고치는 초안이 된다. Conversation 전체에서 이 기능은 에이전트가 말에서 실행으로 넘어가는 경계를 맡는다.

## Tool & Approve System이 주목한 점

"exp_probe.md 권한을 000 으로 바꿔 줘" 같은 요청을 받으면 에이전트는 셸 명령을 실행해야 한다. 기존의 Agent는 대개 둘 중 하나를 택한다. 묻지 않고 실행하면 지우거나 덮어쓰는 명령도 그대로 돌고, 반대로 매번 물으면 `git status` 같은 명령에도 버튼을 눌러야 해서 사용자는 결국 승인 창을 읽지 않고 누르게 된다. 거부한 뒤에는 모델이 도구 대신 "터미널에서 직접 입력하세요" 같은 방법 안내로 빠지기도 한다. 프롬프트에 규칙을 더 적는 방식으로 대처할 수 있지만, 모델이 그 규칙을 지킨다는 보장은 없다. Jarvis-Agent는 위험한 실행은 반드시 사람을 거치게 하되, 사람이 허락한 범위만큼은 기억하고, 거부 뒤의 흐름은 모델이 아닌 코드가 정하도록 설계했다.

### 어떤 기능을 가지고 있나요?

#### 결정은 한 함수, 이유는 세 갈래

- 승인 여부는 `sandbox.decide` 한 곳에서 정한다. 승인 불필요 도구인가, 기억된 규칙에 맞나, 사람에게 물어 어떤 답이 왔나를 이 순서로 보고, 결과는 허용, 거부, 시간 초과 셋 중 하나다.
- 대안으로는 처음처럼 결과를 참/거짓 하나로 두는 방식이 있었다.
- 참/거짓 하나일 때는 120초 동안 답이 없어 거부된 것과 사용자가 거부한 것이 같은 문구로 보여 "승인했는데 왜 거부됐지" 를 설명할 수 없었다. 거부의 이유를 결정 값에 실어 응답 문구와 ACTIVITY 로그를 나눴다.

#### 규칙은 사람이 눌러야만 생긴다

- 승인 규칙은 사용자가 **항상 허용** 을 눌렀을 때만 생기고, 패턴은 서버가 제안하되 좁게 잡는다. `bash` 는 앞 두 단어의 토큰 접두라 `git status --short` 는 통과하지만 `git stash` 는 다시 묻는다. 규칙은 공용과 에이전트별로 나뉜다.
- 대안으로는 모델이나 코드가 규칙을 먼저 만들어 두는 방식이 있었다.
- 승인 기억을 만들 때 가장 경계한 것은 허용 범위가 저절로 넓어지는 일이다. 에이전트가 늘어난 뒤 규칙을 에이전트별로 나눈 것도 KAREN 에서 허용한 명령이 JARVIS 로 번지지 않게 하려는 것이다.

#### 거부 뒤에 모델에게 다시 묻지 않는다

- 한 호출의 도구가 모두 거부되면 루프가 모델을 다시 부르지 않고 정해진 한 줄로 턴을 끝낸다. 일부만 거부됐으면 모델이 나머지 결과로 답을 이어 간다.
- 대안으로는 시스템 프롬프트에 "승인이 필요한 도구도 직접 호출하라, 거부됐어도 새 요청이면 다시 호출하라" 를 넣어 모델이 스스로 지키게 하는 방식이 있었다.
- 거부 결과가 `Execution of 'bash' was denied` 한 줄뿐이던 때, 모델은 이것을 "이 도구는 못 쓴다" 로 읽고 거부 직후 "터미널에서 직접 chmod 000 을 입력하세요" 라고 안내했다. 프롬프트 규칙을 넣자 재요청 때 승인을 다시 묻게는 됐지만, 거부 직후 응답은 여전히 방법 안내였다(gpt-4o-mini, 같은 요청 두 번). 프롬프트로 막히지 않는 것을 코드로 막았고, 효과는 [거부 뒤 승인 흐름 준수](#거부-뒤-승인-흐름-준수) 실험에 있다.

#### 승인 요청은 세션의 모든 창에 간다

- 세션마다 승인 브로커 하나를 두고, 열린 연결 전부에 요청을 보내고, 먼저 온 답을 쓰고, 끝나면 나머지 모달을 닫는다. 기다리는 중에 새로 붙은 탭에도 요청을 다시 보여 준다.
- 대안으로는 처음처럼 승인 요청을 연결(어댑터)마다 따로 다루는 방식이 있었다.
- 승인은 연결이 아니라 세션의 일이다. 같은 세션을 탭 둘에서 보든, 기다리는 중에 새로고침하든 답할 수 있어야 한다.

#### 음성 승인은 거부 쪽으로 기운다

- 말로 받은 승인 답에 부정어가 하나라도 있으면 분류 없이 거부하고, 키워드로 판정이 안 되는 말만 사고 모델에 묻고, 그 답이 분명한 허용일 때만 허용한다. 승인 창이 열려 있는 동안에는 읽기가 끝날 때마다, 인식이 말 없이 끝날 때마다 다시 듣는다(최대 20번).
- 대안으로는 허용과 거부를 같은 무게로 분류하는 방식이 있었다. 듣기 쪽은 처음에 질문을 읽은 뒤 딱 한 번만 들었다.
- 오인식의 비용이 비대칭이다. 거부를 허용으로 잘못 들으면 위험한 명령이 실행되고, 허용을 거부로 잘못 들으면 한 번 더 말하면 된다. gemma4:e2b 로 승인 답 11문장을 돌렸을 때 허용하면 안 되는 말을 허용한 경우는 0건, 판정 중앙값은 0.28초였다. 한 번만 듣던 때는 인식이 몇 초 만에 끝나면 "승인해" 라는 답이 어디에도 닿지 않고 120초 뒤 거부됐다.

#### 절차는 작업 종류마다 하나로 수렴한다

- 같은 (에이전트, 작업 종류)의 절차는 파일 하나다. 성공이 3회 더 쌓여 다음 세대가 되면 아직 승인 전인 초안은 그 자리에서 고치고, 승인된 절차에는 개정 초안을 붙인다. `/procedures approve` 가 본문을 개정으로 바꾼다. 에이전트 하나가 가질 수 있는 절차와 초안은 30개다.
- 대안으로는 처음처럼 세대마다 새 초안 파일을 만드는 방식이 있었다.
- 세대마다 새 파일을 만들면 같은 일을 하는 절차가 성공 횟수만큼 늘고, 사람이 그중 무엇을 승인할지 매번 골라야 한다. EMMA([Niu et al., 2026](https://arxiv.org/abs/2610.35966))는 배운 것을 중복으로 쌓지 않고 한 항목의 수정으로 남겨 기억의 크기를 묶는다(bounded growth). 같은 작업 종류의 성공 30회를 합성해 돌리면 세대 방식은 파일 10개, 수렴 방식은 1개다([절차 파일 수렴](#절차-파일-수렴)).

#### 실패는 범위 하나로 나눠 한 번만 고친다

- 유휴 통합 때 도구 작업이 실패한 턴 일화를 작업 종류별로 묶어 reflector LLM 에 보인다. reflector 는 범위 하나를 고른다. 한 번의 실수(`execution_slip`)는 아무것도 쓰지 않고, 작업 방법이 틀렸으면(`procedure`) 절차 개정 초안을, 주제와 무관한 작업 습관이 틀렸으면(`agent_behavior`) 작업 패턴 초안을 낸다. 제안은 코드 거름망을 지나야 초안이 되고, 초안은 사람이 승인해야 쓰인다.
- 대안으로는 reflector 의 제안을 그대로 쓰는 방식이 있었다.
- EMMA 는 같은 실패를 보여도 백본마다 고르는 수정 종류가 다르고(어떤 모델은 스킬만, 어떤 모델은 에이전트만 늘린다), 범위와 행동을 코드로 묶어야 배운 것이 모델 습관이 아니라 실패를 따른다고 보고했다(Figure 1). 거름망은 모델과 무관한 규칙만 본다. 범위와 행동이 짝이 맞는지, 이번 작업의 정답이나 입력 원문 40자 이상을 옮겼는지, 내용이 1,500자를 넘는지, 새 항목을 만들 자리가 상한 안에 있는지다. 측정 결과는 [실패 반성](#실패-반성-bbeh-mini)에 있다.

ALWAYS 는 지금 에이전트의 규칙 파일에 패턴을 남긴다. 허용 목록과 플러그인의 거부는 is_error 결과로 LLM 에 돌아가고 루프가 이어진다. 사람이 거부했거나 시간이 지나 한 번에 부른 도구가 모두 거부되면 LLM 을 다시 부르지 않고 정해진 한 줄로 턴을 끝낸다. 결과가 모두 오류 없는 final 이면 그 글을 그대로 답으로 쓴다.</figcaption>
</figure>

도구는 `core/tools/` 의 레지스트리에 모이고, 위험할 수 있는 도구는 실행 전에 `core/policy/sandbox.py` 가 사람에게 승인을 묻는다. 도구 호출 한 번은 아래 순서로 지난다.

```mermaid
flowchart TD
  L[LLM 이 도구 호출] --> A{정책 허용 목록}
  A -- 없음 --> E1[is_error 결과: not permitted]
  A --> B{플러그인 before_tool_call}
  B -- block --> E2[is_error 결과: reason]
  B --> C{승인 필요 도구?}
  C -- 아니오 --> X[실행]
  C -- 예 --> D{공용 또는 에이전트 규칙에 맞나?}
  D -- 예 --> X
  D -- 아니오 --> U[사용자에게 묻기<br/>ALLOW / ALWAYS / DENY, 120초]
  U -- ALLOW --> X
  U -- ALWAYS --> W[규칙 저장] --> X
  U -- DENY 또는 120초 시간 초과 --> E3[denied 결과]
  E3 --> Q{한 번에 부른 도구가 모두 거부?}
  Q -- 예 --> Z[LLM 없이 정해진 한 줄로 턴 종료]
  Q -- 아니오 --> R
  X --> P[플러그인 after_tool_call]
  P --> F{결과가 모두 오류 없는 final?}
  F -- 예 --> FA[결과 글을 그대로 답으로]
  F -- 아니오 --> R[결과를 LLM 에]
  E1 --> R
  E2 --> R
```

1. 정책의 허용 목록에 없는 도구면 `not permitted` 오류 결과를 LLM 에 돌려준다.
2. 플러그인의 `before_tool_call` 이 막으면 그 이유를 오류 결과로 돌려준다.
3. 승인이 필요한 도구면 공용 규칙과 에이전트 규칙을 본다. 맞는 규칙이 없을 때만 사람에게 묻는다.
4. 거부는 예외로 처리하지 않는다. 한 번의 호출에서 요청한 도구가 모두 승인을 받지 못하면, 루프는 LLM 에 다시 묻지 않고 정해진 한 줄로 턴을 끝낸다. 다시 물으면 모델이 "터미널에서 직접 이렇게 하세요" 처럼 방법 안내로 빠지기 때문이다. 일부만 거부됐으면 LLM 이 나머지 결과로 답을 이어 간다.
5. 같은 자리에서 도구가 결과를 `final` 로 표시하면, 한 번에 부른 결과가 모두 오류 없는 `final` 일 때 루프는 LLM 에 다시 묻지 않고 그 결과 글을 그대로 답으로 쓴다. 긴 계산표를 작은 모델이 옮겨 적다 줄과 링크를 떨어뜨리는 도구를 위한 것이고, 지금은 `housing_budget` 만 쓴다. 다른 도구 결과와 섞이면 LLM 이 받아 정리한다.

| 경우 | 응답 | ACTIVITY |
|---|---|---|
| `DENY` 를 눌렀거나 음성으로 거부 | 승인이 거부되어 bash 실행을 멈췄습니다. 필요하면 다시 요청해 주세요. | `⚡ approval · …` |
| 120초 동안 답이 없음 | 승인 요청에 시간 안에 답이 없어 bash 실행을 멈췄습니다. 필요하면 다시 요청해 주세요. | `⚡ approval · 시간 초과로 거부` |

시간 초과는 WS `approval_resolved` 에 `timeout: true` 로 실려 열린 모든 창의 모달이 닫힌다. 같은 요청을 다시 하면 승인을 다시 묻는다.

승인이 필요한 도구가 있으면 매 턴 시스템 프롬프트에 규칙을 덧붙인다. 사용자가 실행을 요청하면 도구를 직접 호출하고, 앞에서 거부됐어도 새 요청이면 다시 호출해 승인을 구하라는 내용이다. 도구 루프는 최대 20턴까지 돈다.

### 내장 도구

| 도구 | 하는 일 | 승인 |
|---|---|---|
| `bash` | 셸 명령. 기본 타임아웃 30초 | 필요 |
| `write_file` | 파일 쓰기. 부모 디렉토리 생성, 덮어쓰기 | 필요 |
| `edit_file` | 문자열 정밀 교체 | 필요 |
| `read_file` | 라인 범위 읽기 | |
| `glob` | 패턴으로 파일 찾기, 최근 수정순 | |
| `grep` | 정규식 검색, 바이너리 건너뜀 | |
| `list_dir` | 디렉토리 나열 | |
| `web_search` | Brave(키 있으면) 또는 DuckDuckGo | |
| `web_fetch` | URL 본문을 텍스트로 | |

`lh_notice`, `sh_notice`, `housing_loan`, `housing_budget`, `housing_profile`, `housing_watch` 는 에이전트만 쓰는 도구다. 앱 레지스트리에 넣지 않고, 에이전트 정의의 `tools` 에 이름을 적은 에이전트만 받는다([청약 공고와 대출 계산](../../agents/karen/housing.md)).

`remember_task_pattern` 과 `recall_episodes` 는 모든 에이전트가 쓰는 메모리 도구다. 앞의 것은 사용자가 알려 준 작업 방식을 도구를 부른 에이전트의 작업 패턴으로 저장하고([Memory Management → 작업 패턴](../memory.md#작업-패턴)), 뒤의 것은 그 에이전트의 지난 턴 일화를 조건으로 골라 읽는다.

실행 중에 동적으로 더해지는 도구도 있다. `schedule` 과 `goal`(스케줄러가 켜져 있을 때), `ask_agent`(최상위 에이전트가 둘 이상일 때), `orchestrate` 와 `agent_<name>`(에이전트 정의가 있을 때), `procedure_<name>`(승인된 절차), MCP 서버의 도구, `~/.jarvis/tools/` 의 사용자 도구가 그렇다. 사용자 도구와 MCP 도구는 같은 이름의 내장 도구를 덮어쓴다. 도구 목록은 턴마다 레지스트리에서 다시 읽으므로, 실행 중에 등록된 도구(승인된 절차 등)는 재시작 없이 보인다. `~/.jarvis/tools/` 에 더한 파일도 파일 감시가 켜져 있으면 다음 턴부터 보인다.

### 승인 창과 답

승인 창에서 고를 수 있는 답은 셋이다.

- `ALLOW`: 이번 한 번만 허용한다. Enter 도 같다
- `ALWAYS`: 서버가 제안한 명령 패턴을 기억해 두고 다음부터는 묻지 않는다. 서버가 패턴을 제안했을 때만 보인다
- `DENY`: 실행하지 않는다

승인 여부는 120초 안에 답해야 한다. 그렇지 않으면 자동으로 Deny 처리된다. 음성 모드에서는 말로도 답할 수 있다. 부정어가 하나라도 있거나 판정이 애매하면 거부로 처리한다([음성 승인은 거부 쪽으로 기운다](#음성-승인은-거부-쪽으로-기운다)). `ALWAYS` 로 남긴 규칙이 어떻게 쌓이고 에이전트마다 어떻게 나뉘는지는 [승인 기억](#승인-기억)에서 다룬다.

세션마다 승인 브로커(`ui/web/approvals.py`)가 하나 있다. 승인 요청은 그 세션에 붙은 모든 연결로 가고, 브로커는 먼저 온 답을 쓴다. 기다리는 중에 새로 붙은 탭에도 요청을 보여주고, 답이 정해지면 `approval_resolved` 로 나머지 모달을 닫는다. 연결이 하나도 없으면 바로 거부한다. TUI 에서는 다이얼로그에서 `y`, `a`, `n` 으로 답한다.

### 승인 기억

승인 기억은 사용자가 한 번 허용한 패턴을 규칙으로 남겨 다음부터 묻지 않게 하는 기능이다. 규칙 파일은 두 겹이고, 둘 중 하나라도 맞으면 묻지 않는다.

| 파일 | 누가 쓰나 | 누구에게 적용 |
|---|---|---|
| `~/.jarvis/approvals.yaml` (공용) | 사람이 직접 고친다 | 모든 에이전트 |
| `~/.jarvis/approvals/<agent_id>.yaml` | 승인 화면의 **항상 허용** | 그 에이전트만 |

승인 화면에서 **항상 허용**(TUI `a`, Web `ALWAYS`)을 고르면 서버가 제안한 패턴이 지금 세션의 에이전트 파일에 남는다. 그래서 KAREN 에서 허용한 명령이 JARVIS 로 번지지 않는다. 공용 파일에 이미 있는 규칙이면 아무 파일도 건드리지 않는다. 규칙은 사용자가 그 버튼을 눌렀을 때만 생기고, 모델이 스스로 만들지는 않는다.

:::danger
**항상 허용** 으로 남긴 패턴은 그 뒤로 묻지 않고 실행된다. 지우거나 덮어쓰는 명령에 누르면 그 명령도 다시 묻지 않는다. `bash` 는 앞 두 단어만 맞으면 뒤에 붙는 인자가 무엇이든 통과한다. 되돌리려면 `~/.jarvis/approvals/<agent_id>.yaml` 에서 그 규칙 줄을 지운다. 규칙 파일은 기동 때 읽으므로 지운 뒤 서버를 다시 띄운다.
:::

| 도구 | 제안 패턴 | 대조 |
|---|---|---|
| `bash` | 명령의 앞 두 단어 (`git status`) | 토큰 접두. `git status --short` 는 통과, `git stash` 는 다시 묻는다 |
| `write_file`, `edit_file` | 경로의 디렉토리 (`src/app/*`) | glob |
| 그 외 | `*` | 도구 전체 |

```yaml
# ~/.jarvis/approvals/main.yaml  손으로 고쳐도 된다. 쓰기는 임시 파일 뒤 교체라 중간에 죽어도 깨지지 않는다
rules:
  - {tool: bash, pattern: uv run}
  - {tool: write_file, pattern: "docs/*"}
```

승인이 필요한 도구 목록은 `JARVIS_SECURITY__REQUIRE_APPROVAL_FOR` 로 정한다(기본 `bash`, `write_file`, `edit_file`). 규칙 파일 하나를 앱 전체가 공유한다.

### 에이전트의 경계

승인은 사용자가 대화 중에 있는 일이다. 사람이 없는 차례(목표, 스케줄 작업, 먼저 해 두기)에는 물을 사람이 없어, 에이전트 정의의 `boundaries` 로 미리 정한다. `ask` 도구는 그런 차례에서 빠지고, `never` 도구는 어디서도 보이지 않는다. 자세한 표는 [Goals](./goals.md#경계)에 있다.

### 절차 학습

절차 학습은 여러 번 성공한 작업을 다시 쓸 수 있는 절차로 증류하고, 실패한 작업은 반성해 그 절차나 작업 방식을 고친다. 구현은 `core/procedures/` 에 있다. 자동 학습은 장기 기억의 턴 일화(EDM)에서 정제한다.

```mermaid
flowchart TD
  C[통합: 세션 종료, 유휴 틱] --> V[옛 세대 파일을 작업 종류당 하나로 모음]
  V --> E[EDM: 같은 task_type 의 성공 턴 3회마다 한 세대, 자기 일화만]
  E --> K{이 세대를 이미 다뤘나}
  K -- 예 --> N[건너뜀]
  K -- 아니오 --> D[LLM 증류: 가장 최근 성공 턴의 요청, 도구 단계, 답]
  L[procedures learn] --> F[세션 구간: 도구 3회 이상, 회복하지 못한 오류 0]
  F --> D
  D --> P{같은 작업 종류의 절차가 있나}
  P -- 없음 --> W[새 초안]
  P -- 초안 --> W2[그 초안을 고침]
  P -- 승인됨 --> R[개정 초안으로 붙임]
  V --> X[EDM: 반성하지 않은 실패 턴, 작업 종류별 최근 3개]
  X --> RF[reflector LLM: 범위 하나와 수정 하나]
  RF --> G{거름망}
  G -- 거부 --> RF2[이유를 돌려주고 한 번 더]
  RF2 --> G2{거름망}
  G2 -- 거부 --> Z[기록 안 함]
  G -- 통과 --> S{범위}
  G2 -- 통과 --> S
  S -- execution_slip --> Z
  S -- procedure --> R
  S -- agent_behavior --> TP[작업 패턴 초안]
  W --> A[procedures approve]
  W2 --> A
  R --> A
  TP --> A
  A --> T[도구 procedure_name 과 스킬, 또는 작업 패턴]
```

- **EDM 정제**: 턴 일화는 그 턴에서 성공한 도구 호출(이름과 인자, 인자 값은 200자까지)을 남긴다. 같은 에이전트의 같은 작업 종류(처음 부른 도구)가 3번 성공하면 후보가 된다. 실패한 턴, 도구를 쓰지 않은 대화(`chat`), 다른 에이전트의 일화는 세지 않는다
- **작업 종류당 파일 하나**: 출처가 `edm:<에이전트>:<작업 종류>` 라 같은 작업 종류는 파일 하나다. 성공 3회마다 한 세대이고, 파일의 `generation` 에 마지막으로 다룬 세대가 남는다. 이미 다룬 세대는 LLM 을 부르지 않으므로 통합을 몇 번 돌려도 같다. 다음 세대는 초안이면 그 파일을 고치고, 승인된 절차면 frontmatter 의 `revision` 에 개정 초안으로 붙인다
- **개정 승인**: `/procedures` 목록에 `개정 초안 있음` 이 붙는다. `show` 는 지금 본문과 개정을 함께 보인다. `approve` 는 이름과 출처를 그대로 두고 본문을 개정으로 바꾼 뒤 도구를 다시 올린다. `reject` 는 개정만 버리고 승인된 본문은 남긴다. 버린 세대는 다시 증류하지 않는다
- **상한**: 에이전트 하나의 절차와 초안 파일은 30개까지다. 넘으면 새 작업 종류의 초안은 만들지 않고, 있는 절차의 개정만 받는다
- **옛 세대 파일**: 예전에는 출처가 `edm:<에이전트>:<작업 종류>:<세대>` 라 세대마다 파일이 따로 있었다. 통합 때 이런 파일을 작업 종류마다 하나로 모은다. 승인된 것 중 가장 늦은 세대를 남기고(승인된 것이 없으면 가장 늦은 세대), 그보다 늦은 초안이 있으면 개정 초안으로 붙인다. 밀려난 파일은 지우지 않고 `~/.jarvis/procedures/.archive/` 로 옮긴다. 보관된 파일은 도구로 오르지 않는다. 다 모은 뒤에는 아무것도 바꾸지 않는다
- **실패 반성**: 통합 때 이 에이전트의 실패한 턴 일화 중 아직 반성하지 않은 것을 작업 종류별로 최근 3개씩 묶는다. 유휴 틱 하나에서 많아야 2묶음을 반성한다. reflector 는 묶음마다 한 번 불리고, 출력은 pydantic 스키마(`scope`, `action`, `name`, `when`, `content`, `keywords`)로 읽는다. 스키마에 맞지 않으면 거부로 친다
- **범위와 행동**: `execution_slip` 은 `no_change`(기록 안 함), `procedure` 는 `revise_procedure`(그 작업 종류의 절차가 있으면 개정, 없으면 새 초안), `agent_behavior` 는 `task_pattern`(작업 패턴 초안) 하나만 허락한다. 작업 패턴 초안은 `pattern-<이름>` 파일이고, 승인하면 그 에이전트의 [작업 패턴](../memory.md)이 되고 파일은 지운다
- **거름망**: `update_guard.py` 의 순수 함수다. 범위와 행동의 짝, 내용이 비었거나 1,500자를 넘는지, 작업 패턴의 `when` 과 키워드, 이번 작업의 정답(채점이 있을 때)이 들어 있는지, 실패한 요청에서 40자 이상을 그대로 옮겼는지, 새 항목을 만들 자리가 상한 안에 있는지를 이 순서로 본다. 막히면 이유를 reflector 에 한 번 돌려주고, 다시 막히면 아무것도 쓰지 않는다
- **한 번만 반성**: 반성한 실패 일화에는 결과(`reflected`)와 묶음 키가 남는다. 표시된 일화는 다시 반성하지 않는다. 같은 작업 종류의 반성이 두 번 잇달아 거부되면 그 종류는 LLM 을 부르지 않고 실패만 표시한다(`blocked`). 그 뒤에 같은 작업 종류가 한 번 성공하면 다시 반성한다
- **넘침 근거**: 턴 일화 metadata 에 `overflow` 가 있으면(도구 반복 예산을 다 쓴 턴) reflector 프롬프트에 "한 단계가 너무 컸다" 는 근거로 적는다
- 반성은 `JARVIS_PROCEDURES__REFLECT=false` 로 끈다. 끄면 반성 LLM 호출이 없다
- **세션 구간 학습**: 한 세션에서 도구를 3회 이상 쓴 구간을 바로 배우는 방식은 `/procedures learn` 으로 직접 부를 때만 돈다. 자동으로는 한 번의 성공으로 절차를 만들지 않는다
- 실패한 도구 호출 뒤에 같은 도구가 성공했으면 회복으로 보고 배운다. 실패한 호출은 절차에서 빼고 성공한 경로만 남긴다. 회복하지 못한 오류가 있는 구간은 배우지 않는다
- 같은 구간은 두 번 배우지 않는다. `/procedures learn` 을 다시 불러도 파일이 늘지 않는다
- 이름이 겹치면 해시 접미사가 붙는다
- 증류할 때 입력(`inputs`)만 채우면 그대로 다시 돌릴 수 있는 도구 호출 순서(`plan`)도 받는다. 학습한 작업에서 쓴 도구와 선언한 입력만 쓰는 계획만 남기고, 아니면 버린다
- 계획이 있고 입력이 다 오면 절차 도구가 단계를 차례로 실행한다. 단계마다 세션의 도구 실행기를 거치므로 권한, 플러그인, 승인 검사를 그대로 받는다(절차 안의 bash 도 승인을 묻는다). 실패하거나 승인이 거절되면 그 단계에서 멈춘다
- 계획이 없거나 입력이 빠졌으면 레시피를 돌려주고 에이전트가 따른다. 지시문에는 "단계를 건너뛰지 말고 각 도구 호출을 실제로 실행하라" 가 들어 있다
- 승인된 절차는 그 절차를 배운 에이전트에게만 도구와 스킬로 보인다. KAREN 이 배운 절차는 JARVIS 에게 보이지 않고, 그 반대도 같다. `/procedures` 도 명령을 친 에이전트의 절차만 다룬다. 에이전트가 적히지 않은 예전 절차는 JARVIS(main) 의 것이다
- 도구 목록을 정의에 적은 에이전트(KAREN 등)도 자기가 배운 승인된 절차를 세션을 다시 열지 않고 바로 본다. 다만 절차의 단계는 그 에이전트의 도구 목록 안에서만 실행된다

```markdown
---
name: list-md-files-and-read-readme-summary
description: 마크다운 파일 목록을 보고 README 앞부분을 요약하는 절차
status: approved
source: default#32
tools: [glob, read_file, bash]
parameters: '1. 파일 검색 패턴, 2. 주요 파일 경로, 3. 읽을 최대 줄 수'
---
요청 예: 현재 디렉토리의 md 파일 목록을 보고 README.md 앞 20줄을 읽고 echo done 을 실행해서 요약해줘
이번 입력: {{args}}

절차:
1. glob 으로 파일 목록 검색
2. read_file 로 README.md 20줄
3. bash echo done
```

### 스킬, 플러그인, MCP

- **스킬**: `~/.jarvis/skills/*.md` 에 둔다. `/name args` 가 본문으로 펼쳐져 LLM 프롬프트가 된다. 기동 때 읽고, 파일 감시가 켜져 있으면 바뀔 때 다시 읽는다
- **플러그인**: `~/.jarvis/plugins/*.py` 에 둔다. 실제로 불리는 훅은 `before_agent_start`, `before_tool_call`(block 가능), `after_tool_call`(관찰만, 반환값은 무시), `on_message_end`(응답 교체 가능)다. `transform_context` 는 선언만 되어 있고 호출되지 않는다. 플러그인 하나의 오류는 격리된다
- **MCP**: `mcp_servers` 설정의 서버에서 도구를 발견해 등록한다. `stdio` 와 `http`(SSE) 를 지원하고, 호출마다 새 연결을 연다. 서버 하나가 실패해도 다른 서버는 막히지 않는다. 쓰려면 `uv sync --extra mcp` 로 설치한다

:::note
파일 감시(`JARVIS_PLUGIN__WATCH_FILES`, 기본 켜짐)는 기동 때 있던 도구, 스킬, 플러그인 디렉터리를 지켜본다. 파일을 더하거나 고치면 그 디렉터리만 다시 읽어 같은 이름을 덮어쓰고, 세션은 다음 턴부터 새 도구를 본다. 파일을 지운 도구와 스킬은 재시작 전까지 남는다. 기동 뒤에 만든 디렉터리, 에이전트 정의의 `tools` 로 골라 복사한 도구는 재시작해야 바뀐다.
:::

### 보안 파이프라인

모든 입력은 검증, 인증, 정책 순으로 지난다.

- **검증**: 빈 입력, `JARVIS_SECURITY__INPUT_MAX_LENGTH`(10,000자) 초과, `<script>`, `javascript:`, `on*=` 패턴을 막는다. 통과한 입력은 NFC 정규화와 HTML 이스케이프를 거친다
- **인증**: TUI 는 로컬 사용자로 본다. Web 은 `JARVIS_SECURITY__API_KEYS` 가 있을 때만 키를 요구한다. 키의 `name` 이 메모리 범위와 요청 제한의 사용자 id 가 된다
- **정책**: 현재는 모든 도구를 허용하는 정책이 배선되어 있다. 역할 기반 정책 클래스는 있지만 쓰이지 않는다
- **위험 명령**: 도구 호출의 `command` 인자(셸 도구 `bash`)가 `JARVIS_SECURITY__DANGEROUS_COMMANDS` 의 정규식(대소문자 무시)에 걸리면 승인을 묻지 않고 막는다. "항상 허용" 규칙이 있어도 막는다. 도구 결과에 `security.dangerous_commands` 에 걸렸다고 적어 모델에 돌려준다. 사람 없이 도는 스케줄 작업과 목표 차례도 같은 목록으로 막는다. 기본 목록은 `rm -rf /`, `sudo`, `curl … | sh`, `wget … | sh`, `> /dev/sda`, `mkfs.`, `dd … of=/dev/`, fork bomb 이다

:::warning
위험 명령 목록은 정규식이다. `curl | bash` 처럼 쓰면 `|` 가 "또는" 이 되어 `curl ` 이나 ` bash` 가 든 명령을 전부 막는다. 틀린 정규식은 기동 때 설정 오류로 알린다. 빈 목록(`[]`)이면 차단을 끈다. 파일 내용(`write_file` 의 `content`)은 보지 않으므로 이 목록이 셸 스크립트 파일 작성까지 막지는 않는다.
:::

### 한계

위의 절에 흩어진 한계를 모은다.

- `bash` 의 **항상 허용** 규칙은 앞 두 단어만 본다. 뒤에 붙는 인자는 무엇이든 통과한다
- 규칙 파일은 기동 때 읽는다. 손으로 지운 규칙은 서버를 다시 띄워야 사라진다
- 정책 층은 모든 도구를 허용한다. 역할 기반 정책 클래스는 있지만 쓰이지 않는다
- 위험 명령 목록은 `command` 인자만 본다. `write_file` 로 쓰는 셸 스크립트 내용은 막지 않는다
- 파일을 지운 도구와 스킬은 재시작 전까지 남는다. 기동 뒤에 만든 디렉터리도 재시작해야 읽는다
- 플러그인의 `transform_context` 훅은 선언만 되어 있고 호출되지 않는다
- 실패 반성의 실패 신호는 도구나 모델 오류뿐이다. 답이 틀렸지만 오류가 없는 턴은 실패로 남지 않아 반성하지 않는다
- 턴 일화는 발화와 답을 1,000자까지만 남기므로 reflector 는 긴 요청의 뒷부분(형식 지시가 흔히 놓이는 곳)을 보지 못한다
- EMMA 의 routing(컨트롤러 기억), missing_capability(새 에이전트) 범위와 에이전트 프롬프트 자동 수정은 없다. 작업 습관의 교훈은 프롬프트 대신 작업 패턴 초안으로 간다
- 개정 초안 칸은 하나라 새 개정(성공 증류든 반성이든)이 기다리던 개정을 덮는다
- `/procedures learn` 의 세션 구간 학습은 출처가 구간이라 여전히 구간마다 파일이 생긴다

왼쪽이 사용자와 화면, 가운데가 코드 모듈, 오른쪽이 저장소다. 화살표는 호출이나 데이터의 방향이다.

  SBX -->|승인 필요| BRK[SessionApprovals<br/>ui/web/approvals.py]

## Performance Experiments

거부 뒤의 승인 흐름과 음성 승인 분류가 실제로 안전하게 동작하는지 측정했다.

### 거부 뒤 승인 흐름 준수

- **질문**: 승인을 거부한 직후 모델이 방법 안내로 빠지지 않고, "다시 해 줘" 에는 승인을 다시 묻는가
- **설정**: 승인이 필요한 요청(`chmod 000 exp_probe.md`, `chmod 600 …`, 파일 쓰기)을 보내 승인을 거부하고, 이어서 "다시 해 줘" 를 보낸다. 고치기 전, 프롬프트 규칙만, 규칙과 루프 종료를 함께 넣은 단계를 비교했다. 마지막 단계는 gpt-4o-mini 와 gemma4:e4b 둘로 돌렸다. 떠 있는 백엔드에 WebSocket 으로 요청을 보내고, 승인 창에는 실험 스크립트가 사람 대신 거부로 답한다
- **결과**: Figure 2 (a). 칸은 지킨 횟수/시도 횟수다.

- **한계**: 고치기 전 단계는 실제 사용 기록이다. 재요청 기록은 남아 있지 않다. "프롬프트 규칙만" 단계는 요청 한 번에 거부가 두 번(첫 요청, "다시 해 줘") 있어 분모가 다르다. 시도 수가 단계마다 1~3번으로 작다
- **재현**: `uv run python -m scripts.experiments.agent_turns approval --n 3`(백엔드가 떠 있어야 한다)

### 음성 승인 답 분류

- **질문**: 말로 받은 승인 답을 분류기가 위험하게 허용하는 일이 있는가
- **설정**: 음성 승인 답 12개(허용 4, 항상 2, 거부 4, 애매 2)를 키워드 단계 없이 분류기에만 넣어 모델마다 3회 돌린다(gemma4:e2b, gemma4:e4b, gpt-4o-mini). 실제 화면에서는 이 중 4개("실행해도 돼", "앞으로도 계속 해도 돼", "아직 하지 말고 기다려", "운영 DB 면 절대 안 돼")를 키워드 단계가 먼저 판정하므로, 이 실험은 분류기 단독 성능이다. 결정 정확도는 실행(allow, always)과 거부(deny, unclear)만 맞았는지 본다
- **결과**: Figure 2 (b).

| 모델 | 결정 정확도 | 라벨 정확도 | 위험한 허용 | 놓친 허용(18번 중) | 판정 중앙값 |
|---|---|---|---|---|---|
| gemma4:e2b | 0.917 | 0.78 | 0 | 3 | 0.21초 |
| gemma4:e4b | 1.0 | 0.75 | 0 | 0 | 0.38초 |
| gpt-4o-mini | 0.75 | 0.64 | 0 | 9 | 0.67초 |

- **해석**: 세 모델 모두 위험한 허용이 0 이라, 애매하면 거부하는 설계([음성 승인은 거부 쪽으로 기운다](#음성-승인은-거부-쪽으로-기운다))가 지켜진다. 라벨 정확도가 결정 정확도보다 낮은 것은 거부를 `unclear` 로 본 오답이 결정은 같기 때문이다. e4b 는 라벨 오답 9개가 모두 이런 경우였고, e2b 는 8개 중 5개, gpt-4o-mini 는 13개 중 4개였다
- **한계**: gpt-4o-mini 는 "그거 돌려", "어 써", "앞으로도 계속 해도 돼" 를 세 번 모두 애매하다고 봐서 허용 18번 중 9번 놓쳤다. 다만 "돌려" 는 "되돌려" 로도 읽힐 수 있어 라벨 자체가 애매하다. 놓친 경우 사용자는 한 번 더 말하거나 버튼을 누르면 된다. 12문장은 작은 표본이고, 키워드 단계를 함께 쓴 실제 화면의 정확도는 재지 않았다
- **재현**: `uv run python -m scripts.experiments.reply_classifier --model gemma4:e2b-it-qat --repeat 3`

### 실패 반성: BBEH-mini

- **질문**: 실패한 턴을 반성해 만든 초안을 승인하면 처음 보는 같은 종류의 과제를 더 잘 푸는가. 코드 거름망은 정확도와 수정 종류를 바꾸는가. 같은 실패를 보여도 reflector 백본마다 고르는 수정 종류가 다른가(EMMA, [Niu et al., 2026](https://arxiv.org/abs/2610.35966), Figure 1)
- **설정**: EMMA 가 쓴 BBEH-mini([Kazemi et al., 2025](https://arxiv.org/abs/2502.19187))를 옮겼다. Hugging Face `BBEH/bbeh` 의 `mini` 표시 460문항(23 범주, 범주당 20문항)을 범주마다 seed 42 로 섞어 train 2문항, held-out 8문항씩 나눴다(EMMA 는 4문항과 16문항, 비용 때문에 줄였다). 풀이는 도구 없는 한 턴이고(gpt-4o-mini, temperature 0, BBEH 논문의 답 형식 지시), 채점은 BBEH 공식 `evaluate.py` 의 정확 일치 계열 판정을 그대로 옮겼다. train 결과는 실서비스와 같은 `record_turn` 으로 턴 일화에 쓰고(작업 종류는 범주, 틀리면 실패), 답 앞에 채점 요약(기대한 답, 낸 답)을 붙였다. 그 뒤 실서비스의 `ProcedureLearner.reflect` 를 유휴 틱처럼 빌 때까지 돌리고(틱당 2묶음), 나온 초안을 `/procedures approve` 로 모두 승인했다. held-out 문항 앞에는 그 범주의 승인된 절차 본문과, 질문 낱말에 걸린 작업 패턴(실서비스 `best_matches`)을 붙였다. 실서비스에서 절차는 도구로 노출되고 모델이 불러 본문을 받는데, 도구 없는 실험이라 본문을 바로 넣었다. 수정 종류 분포(b)는 같은 gpt-4o-mini 실패 궤적(train 46문항 중 40문항 실패, 21묶음)을 세 reflector 백본에 보여 거름망을 끄고 켠 결과다
- **결과**: Figure 3. held-out 정확도는 반성 없음 0.158(29/184), 거름망 없는 반성 0.163(30/184), 거름망 있는 반성 0.163(30/184)이다. 같은 문항을 짝지어 보면 반성 뒤에만 맞힌 문항 4개, 반성 뒤에만 틀린 문항 3개다. 학습한 것이 앞에 붙은 문항은 184개 중 65개였다.

| gemma4:e2b | 끔 | 4 | 4 | 10 | 3 | 3 (정답 2, 키워드 없는 작업 패턴 1) |
| gemma4:e2b | 켬 | 6 | 3 | 10 | 2 | 해당 없음 |

- **해석**: 반성은 이 설정에서 held-out 정확도를 의미 있게 올리지 못했다(+1문항, 짝지은 차이 4 대 3). 이유는 셋이다. train 이 범주당 2문항이라 반성 근거가 얇다. 턴 일화가 요청을 1,000자에서 자르므로 reflector 는 BBEH 문항 끝의 형식 지시를 보지 못한다. 작업 패턴은 한국어 키워드로 저장되는데 BBEH 질문은 영어라, 승인한 패턴 14개가 붙은 held-out 문항은 9개뿐이다. 거름망은 gpt-4o-mini 에서는 한 번도 막지 않았다. 범위와 행동이 늘 짝이 맞았고 정답이나 원문을 옮기지 않았다. gemma4 두 모델에서는 거름망 없이 받아들인 제안 중 각각 3개가 거름망에 걸렸을 것이었다(대부분 이번 문항의 정답을 절차에 적은 것이다). 거름망을 켜자 이런 제안은 이유를 받고 고쳐 다시 내거나, 다시 막혀 기록되지 않았다. 수정 종류는 백본마다 갈렸다. 같은 실패를 보고 gpt-4o-mini 는 모두 무엇인가를 기록했고(작업 패턴 14, 절차 7), gemma4:e4b 는 대부분 절차 개정을 골랐고(15/21), gemma4:e2b 는 절반 가까이를 한 번의 실수로 보고 기록하지 않았다(10/21). EMMA 가 본 "수정 종류가 백본의 습관을 따른다" 는 현상은 Jarvis 의 세 범위에서도 나타난다. 거름망은 종류의 습관까지 바꾸지는 않고(그 선택은 백본 몫이다), 범위를 벗어나거나 정답을 담은 수정만 막는다
- **한계**: held-out 184문항, gpt-4o-mini 한 백본, 한 번 실행이라 1문항 차이는 잡음 안이다. EMMA 처럼 수정 뒤 같은 과제를 다시 풀어 시험하는 사슬(attempt chain)은 없고, 수정은 승인 뒤 다음 과제부터 쓰인다. 실서비스의 실패 신호는 도구나 모델 오류뿐이라, 채점 요약을 답에 붙인 이 설정은 실서비스보다 근거가 많다. 절차는 실서비스처럼 도구로 부르지 않고 본문을 바로 넣었다. (b) 의 거부에는 거름망 거부와 스키마에 맞지 않는 출력이 함께 들어 있다
- **재현**: `uv run python -m scripts.experiments.procedure_reflection --part emma2`(BBEH 데이터는 `~/.jarvis/benchmarks/bbeh/bbeh_data.json`, LLM 출력은 `~/.jarvis/benchmarks/bbeh/cache/` 에 캐시되어 다시 돌리면 LLM 을 부르지 않는다)

### 절차 파일 수렴

- **질문**: 같은 작업 종류의 성공이 쌓일 때 절차 파일이 늘지 않고, 예전 세대 파일이 쌓인 디스크도 데이터를 잃지 않고 하나로 모이는가
- **설정**: LLM 없이 합성 성공 일화로 잰다. KAREN 의 같은 작업 종류(`lh_notice`) 성공을 0회에서 30회까지 3회씩 쌓고, 매번 통합(`refine`)을 돌리고 새 초안은 바로 승인한다. 세대 방식은 이전 코드의 출처 규칙(세대마다 새 파일)을 그대로 센다. 수렴 방식은 지금 `ProcedureLearner` 를 실제로 돈다. 따로, 1세대 승인과 2세대부터 10세대까지의 초안이 쌓인 옛 디스크에 `converge` 를 두 번 돌리고, 작업 종류 40개가 각각 3번 성공했을 때 상한을 본다
- **결과**: Figure 3 (c). 성공 30회에서 세대 방식은 파일 10개, 수렴 방식은 1개다. 증류 LLM 호출은 두 방식 모두 세대마다 한 번(10번)이다. 옛 디스크의 파일 10개는 1개(승인 유지, 10세대 초안을 개정으로 붙임)로 모였고 9개는 `.archive/` 로 옮겨졌다. 두 번째 `converge` 는 아무것도 바꾸지 않았다. 작업 종류 40개는 상한 30개에서 멈췄고 증류 호출도 30번이었다
- **해석**: 출처에서 세대를 빼자 사람이 고를 절차가 작업 종류마다 하나로 줄었다. 새 세대는 개정 초안으로 기다리다가 승인할 때 본문을 바꾼다. 옛 파일은 지우지 않고 보관하므로 수렴을 되돌릴 수 있다
- **한계**: 합성 일화라 증류 결과의 품질은 보지 않았다. 개정 칸은 하나라 승인 전에 다음 세대가 오면 앞 개정을 덮는다. 상한 30은 정한 값이고 측정으로 고른 값이 아니다
- **재현**: `uv run python -m scripts.experiments.procedure_reflection --part emma1`
